# Architecture

The repository is split into three boundaries (the Java backend is described in its own section below):

- `packages/shared`: config schemas, public and per-player projection types, default configs and presentation helpers for the browser. It has no engines and depends only on `zod`.
- `backend`: the Java server, the only server and the only place with game engines. It serves the whole HTTP API, hosts rooms over the `/ws` WebSocket with all 31 engines, runs data-sync and owns the schema (Flyway). The coordinator sends intentions to a registered game module and publishes only its public projection.
- `frontend`: React screens and presentation. It never decides deadlines, winners, eliminations or whether a selection wins a race.

The English sections from «Local data authority» on were written for the Node server. They still describe the design, because the Java backend ports it literally (same rules, projections, timers and limits); file names there point to the removed Node server (`apps/server`, in git history before the commit «Quitar el servidor Node y los motores TS»), and the Java counterparts are listed in the Spanish sections.

## Backend Java (etapa 1)

`backend/` es un servicio Micronaut 5.1.5 (Java 25, Gradle 9.8.2). Empezó en la etapa 1 conviviendo con `apps/server` detrás del mismo origen (migración por estrangulamiento) y desde el corte 2D es el único servidor; el diseño completo está en `docs/superpowers/specs/2026-10-31-separacion-frontend-backend-java-design.md` y lo que queda en `docs/migracion-java-pendientes.md`.

**Fronteras.** Desde el corte 2D Java es la autoridad de las partidas y el único proceso que lee y escribe PostgreSQL en producción. En la etapa 1 solo atendía REST sin estado de sala y compartía la BD con Node; las secciones de cada etapa cuentan qué se añadió en cada una.

**Rutas que nginx manda a Java.** Desde el corte 2D, todas: `location ^~ /api/` y `location = /ws` hacia `backend:8080` (`infra/nginx.conf`), igual que el proxy de Vite en desarrollo. `proxy_pass` sin URI reenvía la ruta sin normalizar; las variantes de `/api/admin` acaban en 401/403 o 404 (`AdminGateTest`). `/health` y `/prometheus` del backend no se enrutan desde nginx.

**Capas.** `domain/` (reglas puras) y `application/` (casos de uso y puertos) no dependen de los adaptadores REST: los servicios lanzan los errores de `application/errors` (`BadRequestException`, `ConflictException`, `NotFoundException`, `UnauthorizedException`) y `ApplicationExceptionHandler` les pone el estado HTTP; el perfil se compone como `UserProfile` y el controlador lo convierte en `ProfileResponse`; `GameRegistry` es una clase pura y su bean lo crea `adapters/out/resources/ClasspathGameRegistryLoader` desde `games/registry.json`. Concesiones deliberadas de la etapa 1: los records de dominio que se serializan tal cual (`GameManifest`, `AuthUser`, `AvatarRef`, `Pokemon`) llevan anotaciones de Micronaut Serde (solo anotaciones, sin lógica del framework), y los servicios de aplicación usan directamente las entidades y repositorios de `adapters/out/persistence` porque no se definieron puertos de repositorio; se revisará al ampliar el backend.

**Identidad.** Java firma y acepta la misma cookie `pu_session` que emitía Node, así que las sesiones abiertas antes del corte siguen valiendo (JWT HS256 con `JWT_SECRET`, HttpOnly, SameSite). Las contraseñas se verifican con bcrypt (at.favre, estrategia de truncado a 72 bytes igual que bcryptjs), de modo que las cuentas existentes siguen entrando.

**Esquema: Flyway, único dueño.** Desde el corte 2D el esquema lo crea y migra solo el backend Java. Al arrancar, `FlywayMigrations` (fuera de `test`, con baseline-on-migrate en la versión 1, validación y `clean` desactivado; en `test` la migración automática de Micronaut, sin baseline porque la BD de Test Resources parte vacía) aplica `backend/src/main/resources/db/migration/`: en una BD vacía, `V1__baseline.sql` crea el esquema completo; una BD creada por Prisma que ya tiene `flyway_schema_history` (producción desde la etapa 1) arranca sin cambios; una BD creada por Prisma sin historial se registra en baseline 1 sin ejecutar `V1`. `FlywayMigrationsTest` comprueba los tres casos, que `V1__baseline.sql` y las migraciones de Prisma (copia congelada en `backend/src/test/resources/db/prisma-migrations/`) dan el mismo `pg_dump --schema-only`, y que una BD vacía migrada hasta la última versión queda igual que una BD de Prisma en baseline 1 migrada hasta la última (con una migración de sonda solo de test, `db/testmigration/V9999__probe.sql`). Regla: **los cambios de esquema son migraciones Flyway `V2__…`**; nunca se edita una migración aplicada. `/api/health` informa en `schemaVersion` la última migración Flyway correcta («`1 baseline`», «`2 add x`»…; sin historial de Flyway, `unknown`). `V16` borra `_prisma_migrations`, el historial de Prisma que conservaban las BD creadas por Prisma. El backend usa Hibernate 7 vía Micronaut Data JPA con identificadores entrecomillados para coincidir con los nombres de Prisma.

**Avatares.** El backend corre como uid/gid 1000, igual que el usuario `node`, y monta el mismo volumen de avatares: los ficheros que escribió Node tienen modo 0600 y otro uid no podría servirlos ni borrarlos. Un avatar es `DEFAULT` (la inicial del nombre, sin fichero) o `CUSTOM` (una imagen subida, `<uuid>.webp`); los avatares predefinidos se retiraron (`V2__avatares_sin_predefinidos.sql` pasa los `PRESET` guardados a `DEFAULT`, y los tokens antiguos con `PRESET` se leen como `DEFAULT`). Desde 2C Java también escribe avatares (`POST /api/auth/guest/custom-avatar`, `PUT /api/auth/profile/avatar/custom`, `DELETE /api/auth/profile/avatar`, que vuelve a `DEFAULT`), y desde el corte 2D se le enrutan en dev/E2E y en producción (nginx admite cuerpos de hasta 10 MB, el `max-request-size` de Micronaut). `AvatarImageProcessor` detecta el formato por los bytes (debe coincidir con el `Content-Type`), lee las dimensiones de la cabecera antes de decodificar (más de 4096² píxeles es «archivo no válido», un lado fuera de 64..4096 el literal de dimensiones), aplica la orientación EXIF de los JPEG, recorta `cover` a 256×256 y codifica WebP calidad 84. Lectura en Java puro (TwelveMonkeys JPEG/WebP, PNG del JDK); escritura con la libwebp nativa de `webp-imageio`, que la imagen Docker copia a `/app/native` (`java.library.path`) por si `/tmp` es `noexec`. El limitador de avatares (12 por 15 min por IP, un contador para las tres rutas) ignora `RATE_LIMIT_DISABLED` y corre después de `IdentityFilter`, porque en las rutas de perfil un 401 no cuenta. Cada cambio de un usuario registrado reemite `room:state` de su sala (`config/AvatarWiring` → `RoomCoordinator.updateIdentityAvatar`).

**Contrato REST para la web.** El OpenAPI se genera al compilar (`backend/openapi/pokemon-universe.yml`, versionado). `verifyOpenApi` forma parte de `check` y falla si la copia versionada difiere; el procesamiento incremental de anotaciones está desactivado para que la salida sea determinista. La web genera sus tipos con `npm run api:types -w @pokemon-universe/web` (`frontend/src/lib/api-types.ts`). Los manifiestos y las configuraciones por defecto de los minijuegos se escriben a mano en `backend/src/main/resources/games/registry.json`; `registry-defaults.test.ts` (en `packages/shared`) falla si una `default<Juego>Config` del frontend no coincide, y `npm test` ejecuta además `check:api-types`. Los 400 de rutas que validan con esquemas Zod portados (`InvalidInputException`, p. ej. `/api/categories` y `/api/would-you-rather-prompts`) llevan las incidencias de Zod completas y se documentan con el esquema `ValidationErrorResponse` (`{error, issues: ZodIssue[]}`, `ZodIssue` = `{code, path: (string|integer)[], message}` más claves por código); el resto de 400 sigue con `ApiError` (en los dilemas, crear y editar documentan `oneOf` de ambos: «opciones iguales tras normalizar» lo lanza el servicio y no lleva `issues`, como en Node). micronaut-openapi 7.1 elimina `additionalProperties: false` al normalizar, así que los cuerpos estrictos lo indican en su descripción.

**Operación.** Respuestas JSON con inclusión global NON_NULL. Errores con el mismo formato que Node (`{"error": "...", "issues"?: [...]}`): las excepciones propias pasan por `ExceptionHandler` y los errores que genera Micronaut (404, 405, 415, cuerpo ausente) por `ApiErrorResponseProcessor`, que sustituye el cuerpo HATEOAS. Límites de peticiones en memoria (global 120/min, autenticación 30 por 15 min, feedback 10 por 15 min, cabeceras draft-7), válidos para una sola instancia. Salud en `/health/{liveness,readiness}`, métricas en `/prometheus`, logs JSON en producción (`-Dlogback.configurationFile=logback-prod.xml`). La imagen JVM se construye desde `build/docker/main/layers`; la imagen nativa compila pero falla al arrancar y no se despliega (ver pendientes).

## Salas en Java (etapa 2A)

Desde la etapa 2A el backend Java puede alojar salas completas (lobby, rotación, votación, resultados) con `application/rooms/RoomCoordinator`, port literal de `apps/server/src/rooms/manager.ts` con una sección crítica por sala. Hasta el corte 2D fue solo de desarrollo y E2E, porque el cambio de transporte y de rutas era todo o nada (ver «Corte 2D» en `docs/migracion-java-pendientes.md`); desde el corte es el coordinador de producción. En 2A había dos motores portados (`higher-lower` y `pokedex-distance`); desde 2B están los 28 (hoy 31) (ver la sección siguiente). `ClasspathGameRegistryLoader` no arranca si algún manifiesto no tiene motor, así que todo juego publicado se puede jugar; `/api/games` y el perfil muestran los 31 manifests. El coordinador reparte el trabajo en colaboradores que reciben la sala ya bloqueada: `RoomChatCommands` (chat del lobby), `GameRotation` (pares jugables y azar de la rotación), `NextGameVoting`, `DailyRoomLifecycle` (final de la sala del reto), `CursorRelay` y `RoomViews`.

**Transporte.** Desde el corte 2D la web usa siempre el WebSocket nativo contra `/ws` (`createRealtime()` de `frontend/src/lib/socket.ts`, cliente en `realtime-ws.ts`); el adaptador Socket.IO y la bandera `VITE_REALTIME` ya no existen. `RoomContext` solo conoce la interfaz `RealtimeClient`. En desarrollo el proxy de Vite manda todo `/api` a `http://localhost:8080` y `/ws` a `ws://localhost:8080`; en contenedores, nginx tiene `location = /ws` (coincidencia exacta) hacia `backend:8080`.

**Interruptor del servidor.** `pu.rooms.enabled` (`ROOMS_ENABLED`, por defecto `false`; `true` en `application-dev.yml` y `application-test.yml`). Apagado, `@OnOpen` de `/ws` cierra la sesión con 4403 «Rooms disabled» antes de registrarla y el coordinador no llega a verla (así estuvo producción hasta el corte). Desde el corte 2D, `compose.yaml` lo fija a `true` (sin variable `PU_…`), igual que `INTERRUPT_STALE_ROOMS` (`pu.interrupt-stale-rooms`: al arrancar marca `INTERRUPTED`/`SERVER_STOPPED` las salas `ACTIVE` y las partidas `IN_PROGRESS` del proceso anterior) y `BACKEND_DATA_SYNC_ENABLED`; los tres siguen a `false` por defecto en el código para que pruebas y arranques sueltos no los enciendan (`config/ComposeStartupTest` arranca con el entorno de compose).

**Protocolo `/ws`.** Identidad desde la cookie `pu_session` en el *handshake*; sin cookie o con una inválida el servidor completa el *upgrade* y cierra en `@OnOpen` con 4401 «Authentication required» (el navegador no puede leer un rechazo HTTP del *handshake*, sí un código de cierre). Mensajes JSON con sobre: el cliente envía `{id, event, payload}` y recibe `{id, ok, data | error}` como ack (también ante cualquier error inesperado); el servidor empuja eventos con los mismos nombres y payloads que `ClientToServerEvents`/`ServerToClientEvents` de Socket.IO, incluido `session:restored` cuando una conexión de un miembro conocido se engancha a la sala (`session:attach`, ver «Amigos e invitaciones»). Cada conexión procesa sus mensajes en orden sobre hilos virtuales.

**Latido y límites.** Ping cada 25 s (`pu.ws.heartbeat-seconds`, el `pingInterval` de Socket.IO) para que Netty no cierre salas tranquilas por inactividad; nginx usa `proxy_read_timeout`/`proxy_send_timeout` de 75 s, por encima del latido. Un cliente muerto (sin pongs ni mensajes) se detecta con `micronaut.server.read-idle-timeout` de 60 s (`WS_READ_IDLE_TIMEOUT`, ≈ 2,4 latidos, el papel del `pingTimeout` de Socket.IO): Netty cierra la conexión y el coordinador recibe la desconexión; `idle-timeout`/`write-idle-timeout` quedan en 10 min (`SERVER_IDLE_TIMEOUT`). Mensajes de más de 32 768 bytes (`maxHttpBufferSize` de Node) cierran con 1009. Límite de 50 eventos por ventana de 10 s y conexión, aplicado antes de encolar y sin contar los de cursor.

**E2E.** `npm run test:e2e` ejecuta todos los specs contra el backend Java (Playwright ya no arranca Node).

## Amigos e invitaciones

**Datos.** Tabla `Friendship` (`V7__amigos.sql`): una fila por pareja sin orden (índice único sobre `LEAST/GREATEST` de `requesterId`/`addresseeId`), `status` `PENDING` o `ACCEPTED`, `createdAt` y `acceptedAt`; borrar una cuenta borra sus filas en cascada. Rechazar, cancelar o quitar a un amigo borra la fila. Solo cuentas registradas: un invitado no tiene amigos ni presencia.

**REST.** `/api/friends` (`FriendsController` → `FriendService`), solo para cuentas registradas: `GET /api/friends` (amigos con su presencia, solicitudes recibidas y enviadas), `POST /api/friends/requests` (por nombre de usuario, sin distinguir mayúsculas; si el otro ya te la había pedido, os hace amigos), `POST /api/friends/requests/{id}/accept`, `DELETE /api/friends/requests/{id}` (rechazar o cancelar) y `DELETE /api/friends/{userId}`. Una solicitud imposible responde siempre «Cannot send a friend request to this user», exista o no la cuenta. Límites: 200 amigos aceptados («Friend limit reached»; si al aceptar o cruzar una solicitud el lleno es el otro, «That user has reached the friend limit», que no revela nada porque los dos ya se pidieron la amistad) y 50 solicitudes enviadas pendientes («Too many pending requests»), además del limitador `friendRequests`.

**Eventos `friends:*`.** Por el mismo `/ws` y solo a cuentas registradas: `friends:presence` `{userId, status}` (`OFFLINE`, `ONLINE`, `IN_ROOM`, `PLAYING`), `friends:changed` (la amistad o una solicitud entre los dos cambió: el cliente vuelve a pedir `GET /api/friends`) y `friends:invite`. `FriendPresence` calcula el estado de una cuenta con sus conexiones abiertas (`WsSessions`) y su sala (`RoomCoordinator.occupancyOf`) y, si cambió, se lo envía solo a sus amigos aceptados conectados, en todas sus conexiones; nunca a desconocidos ni a quien solo tiene una solicitud pendiente. Abrir o cerrar cualquier conexión de la cuenta, entrar o salir de una sala y empezar o acabar una partida lo recalculan; los avisos se agrupan por cuenta fuera del lock de la sala.

**`room:invite`.** `{userId}` (`RoomInvitations`): solo a un amigo aceptado y conectado, desde la sala de quien invita y solo en su lobby («Invitations are only available in the lobby»), si el amigo no está ya en ella y hay plaza. Envía `friends:invite` a todas las conexiones del amigo; la invitación no se guarda y caduca a los 10 minutos. Una por pareja cada 30 s y 10 por anfitrión por minuto, en memoria. Aceptar es un `room:join` normal con el código.

**Conexión abierta frente a asiento.** La web de una cuenta registrada mantiene el `/ws` abierto en toda página (`SessionRoot` → `RoomProvider`), para la presencia y las invitaciones; la de un invitado, solo en `/play` y `/room`. Abrir la conexión no toca la sala: solo una conexión **enganchada** ocupa el asiento del jugador (`member.connectionId`), recibe `room:state` y puede mandar comandos de sala (`assertActiveSocket`). Se engancha con `session:attach` (que restaura al miembro y le envía `session:restored`), con `room:create` o con `room:join`. El cliente envía `session:attach` mientras `RoomSessionLayout` (`/play` y `/room`) está montado, al montarse y en cada apertura del socket, antes que cualquier otro comando (`room/session-attachment.ts`). Así otra página o pestaña de la misma cuenta fuera de la sala no le quita el asiento a la de la sala, y cerrarla no la desconecta (`disconnect` ignora conexiones que no son la vigente). Dos pestañas en la sala: gana el último enganche y la otra recibe «Estás jugando en dos pestañas…». Navegar a otra página en la misma pestaña conserva el asiento (no hay desenganche); se libera con «Salir», una expulsión (`room:kicked`), cerrar sesión o cambiar de cuenta, o al cerrarse esa conexión, con la gracia de reconexión de siempre. La pestaña que ya se enganchó una vez lo recuerda (`attached`): si su socket reconecta estando fuera de `/play` y `/room`, la conexión nueva también envía `session:attach` y conserva el asiento; una pestaña que nunca estuvo en la sala no se engancha.

**Chat del lobby.** Los miembros de una sala hablan por el mismo `/ws`, con tres órdenes (`room:chat:send {text}`, `room:chat:delete {seq}` y `room:chat:mute {playerId, muted}`) que pasan por `current()`, es decir, solo las manda la conexión enganchada. Los eventos llegan solo a los miembros con conexión: `room:chat:message {roomInstanceId, message}`, `room:chat:deleted {roomInstanceId, seq}` y `room:chat:history {roomInstanceId, messages}`, que se envía al unirse y al restaurar la sesión (`session:attach`). El silencio (`chatMuted` en cada miembro de `room:state`) y los mensajes viven en memoria, en la sala (`RoomChat`): no hay migración, ni tabla, ni ruta REST, y todo desaparece con ella. Borrar y silenciar exigen `MODERATE_CHAT` (Host y Co-host); el chat solo funciona en el lobby.

## Motores y assets en Java (etapa 2B)

Plan: `docs/superpowers/plans/2026-10-31-etapa-2b-motores.md`. Solo desarrollo y E2E hasta el corte 2D; en producción desde entonces.

**Motores (31/31).** Cada motor está en `backend/src/main/java/es/pokemonuniverse/domain/game/engines/<id sin guiones>/` y se registra en un único sitio, `portedEngines` de `adapters/out/resources/ClasspathGameRegistryLoader.java`, en el mismo commit que sus fixtures doradas. `GoldenRegistryConsistencyTest` falla si hay fixtures sin motor o motor sin fixtures, y el cargador exige un motor por manifiesto (`ClasspathGameRegistryLoaderTest` lo comprueba con los 31). Las reglas de port (orden de claves, `Record<number, …>`, token de asset, `localeCompare`, `.int()`, `trim()`, `\p{Diacritic}`) están en `domain/game/engines/README.md`. Las condiciones compartidas por Bingo y Bluff Auction viven en `domain/pokemon/conditions/`.

**Arnés dorado.** Las fixtures las generaban los motores TS; desde que se quitaron, las graba Java (`GoldenRecorder`, con `./gradlew test -Dupdate=true --tests '*GoldenReplayTest*'`) y son fotos de su comportamiento: al cambiar un motor se regraban y se revisa el diff. `golden/OrderedJsonCompare` compara los objetos clave a clave **en secuencia** (el orden de claves grabado es el contrato del cable; `JsonTree.equal` de producción sigue ignorándolo). Un escenario puede traer contexto (`hostCustomCategories`, `hostWouldYouRatherPrompts`, `pokemonVisuals`, `pokemonAudio`, `tcgCards`) que `GoldenContexts.java` monta, un `catalogPatch` con paletas y pasos `asset` que fijan `resolveAsset`. El flujo está en `domain/game/engines/README.md`.

**Catálogo.** `application/pokemon/PokemonCatalogService` carga además movimientos, learnsets, evolución y entradas de Pokédex (`LearnsetPokemonCatalog`, `PokedexEntryPokemonCatalog`) y las paletas de `metadata` con las reglas del cargador de Node (`catalog.ts`, en `CatalogPalette`), no con las del data-sync. Los nombres se ordenan con `domain/text/Collations.names()`: collator ICU4J raíz, terciario y congelado, con la misma ICU mayor que Node (78.3; `java.text.Collator` ordena distinto). La web solo ve el catálogo por el buscador: `GET /api/pokemon/selector?generations=…&includeForms=…` devuelve `{ pokemon: [{ id, name, sprite }] }` ordenado por nombre (`Collations.names()`, forma por defecto primero y después id; el orden por número de Pokédex filtraba el número por la posición), sin número, generación, tipos, estadísticas ni sprite shiny, con `Cache-Control: no-cache` y un `ETag` débil (16 hex del SHA-256 del JSON servido): cambia cuando cambia la proyección `id`/`name`/`sprite` de la respuesta (por ejemplo, tras una recarga del catálogo que añada, quite o renombre Pokémon); una recarga que solo toque otros campos no lo cambia. `If-None-Match` igual responde `304`. El `sprite` es opaco, `/api/pokemon/{id}/sprite` (el id es el slug de PokéAPI, no el número): Java descarga la imagen original con la lista de orígenes de confianza de los assets de ronda, pero con su propio `GameAssetService` y su propia `ResourceCache` (`PokemonSpriteService`: 16 MiB, 4096 entradas, concurrencia 8, 512 pendientes) para que las miniaturas no expulsen los assets precargados de las rondas; responde `public, max-age=86400`, `404` si el id no está en el catálogo, `502` si el origen no devuelve un `image/*` y `503` por capacidad. `GET /api/pokemon` (el catálogo completo) ya no existe. Esta carga más pesada (todos los movimientos, cada fila de learnset y cada entrada de Pokédex por JPA) se repite en cada recarga horaria; la recarga es de un solo vuelo (`CatalogSnapshotCache`: lectura `volatile` sin cerrojo en caliente y relleno `synchronized` con doble comprobación), así que N peticiones al caducar ejecutan una sola carga (`PokemonCatalogServiceCacheTest`). Subir `icu4j` en `backend/build.gradle.kts` puede cambiar algún orden de nombres: hay que regrabar las fixtures doradas y revisar el diff. Otros equivalentes de JS: `domain/json/JsNumbers.isSafeInteger` para `.int()` de Zod, `JsStrings.trim` para `trim()` y `UProperty.DIACRITIC` de ICU para `\p{Diacritic}`.

**Proxy de imágenes y gritos de ronda.** `adapters/in/rest/rooms/GameAssetController` sirve `GET /api/rooms/{code}/games/{assetToken}/rounds/{roundNumber}/options/{optionId}/sprite` y `/audio` sin autenticación, como Node: pide la resolución a `RoomCoordinator.gameAsset`; `roundNumber` no entero o resolución vacía → 404 sin cuerpo; `/audio` con un tipo que no es `audio/*` ni `application/ogg` → 415; éxito con `Cache-Control: private, max-age=86400, immutable`; capacidad agotada → 503 con el literal de Node. `application/assets/GameAssetService` aplica la transformación (`domain/game/assets/ImageTransforms`: normalizado 512, recorte con zoom, silueta 320, pixel art y recoloreado 192) sobre `ResourceCache` (LRU de 32 MiB / 256 entradas, 8 cargas concurrentes, 64 pendientes, deduplicación en vuelo) y precarga lo que piden los motores. `adapters/out/assets/TrustedAssetSourceLoader` solo acepta `https://raw.githubusercontent.com/…` o `local-artwork:<id>` (regex `^local-artwork:([a-z0-9]+(?:-[a-z0-9]+)*)$`), con 15 s de plazo y 8 MiB de tope. La paridad con `sharp` es por propiedades, no por bytes (lienzo, alfa, silueta con RGB 0, foco y recoloreado exactos): el bilineal de Java2D frente al lanczos3 de sharp deja siluetas ≈ 3 px más estrechas (medido en Voltorb y Pikachu).

**Catálogos visual y de audio.** `adapters/out/storage/FilesystemArtworkCatalog` escanea los PNG de `pu.artwork-dir` (`POKEMON_ARTWORK_DIR`; en dev, `assets/pokemon-artworks` relativo a `backend/`; en la imagen, `/app/pokemon-artworks`, copiado desde `backend/assets/pokemon-artworks`) cuyo nombre es un id del catálogo y con ≥ 0,2 % de píxeles visibles; sin directorio, catálogo vacío con un aviso. `adapters/out/persistence/JpaPokemonAudioCatalog` lee los gritos de `PokemonAssetReference` y de `metadata.cries` (solo `https://raw.githubusercontent.com/PokeAPI/cries/`). Los tres catálogos viajan juntos en `GameCatalogs` (`RoomCoordinator.replaceCatalog`). Las salas Java pasan como `tcgCards` el `application/tcg/CachedTcgCardCatalog` compartido (no se fija por partida, como en Node; `refresh()` sustituye la lista de una vez), que se carga al arrancar (`config/TcgCatalogStartup`, con las salas encendidas, aunque el data-sync esté apagado) y tras cada sincronización TCGDEX completada (`onCompleted`, registrado en `config/DataSyncBeans`); `/api/tcg/options` y `/api/tcg/eligibility` (`adapters/in/rest/tcg/TcgController`) lo leen y en desarrollo se enrutan a Java como el resto de `/api`. Además, un `HostContentProvider` (`config/RoomBeans`) con las categorías activas del host de `CustomCategoryService` y sus pares activos de Would You Rather de `WouldYouRatherPromptService` (cachés de todos los usuarios cargadas al arrancar con las salas encendidas; cada mutación de `/api/categories` o `/api/would-you-rather-prompts` reemite `room:state` si el usuario es host, `config/HostContentWiring`). Los dilemas serializan las mutaciones de cada usuario (lock justo por usuario; un fallo no bloquea la siguiente), importan de 1 a 100 en una transacción (todo o nada) y editan en una transacción `SERIALIZABLE` (`adapters/out/persistence/WouldYouRatherPromptWriter`) con hasta 3 intentos ante `40001`/`40P01`; `23505` es el 409 de pareja duplicada. El refine «opciones distintas» compara con el colador ICU `es` de fuerza primaria, como `localeCompare(…, {sensitivity: 'base'})`.

**Límite y AWT.** Las rutas `^/api/rooms/[^/]+/games/` quedan fuera de la política global de 120/min y tienen la suya, `gameAssets`, de 5000/min por IP (`RateLimitPolicy`). ImageIO necesita AWT sin pantalla: `Application.main` fija `java.awt.headless=true` y el `Dockerfile` lo repite en `JAVA_TOOL_OPTIONS`; la base sigue siendo `eclipse-temurin:25-jre-alpine`.

**Enrutado.** Las URL de assets que emiten los motores son relativas (`/api/rooms/…`). En dev, `proxyFor` de `frontend/vite.config.ts` manda todo `/api` (también `/api/rooms/`) a `:8080`. `infra/nginx.conf` las manda también a Java (`location ^~ /api/`) desde el corte 2D.

**E2E por juego.** `e2e/tests/juegos.spec.ts` (`npm run test:e2e -- juegos`) lanza los 31 juegos contra el `/ws` de Java y exige que ninguna página abra Socket.IO. `tcg-higher-lower` y `pokemon-palette-guess` se saltan solo si el servidor muestra su literal de no disponibilidad (sin cartas TCG o sin paletas en la BD). El encaje se anota y solo falla con `PU_LAYOUT_STRICT=1` (ver `e2e/README.md`).

## Local data authority

All gameplay data is read through server repositories and services backed by
PostgreSQL. The immutable in-memory Pokémon catalog is only a read cache rebuilt
from PostgreSQL at startup and after successful PokéAPI synchronizations; it is never populated directly from an external API. Each active game retains its original catalog, audio and visual references and an opaque catalog revision. Refreshes replace all three references together for new games. Pokémon objects and nested metadata are copied and frozen. TCG decks copy their comparable prices when created.

External sources are isolated under `apps/server/src/data-sync/`:

```text
PokéAPI / TCGdex -> DataSyncService -> PostgreSQL -> repositories -> games/web
```

On first boot, a missing Pokémon dataset is synchronized before rooms become
available. TCGdex initializes in the background; TCG Higher/Lower declares its catalog availability to the coordinator and is excluded from playable rotations until its configured filters provide at least two comparable cards. Later runs are incremental: PokéAPI checks for dataset growth and TCGdex
refreshes persisted prices daily. Failed runs are recorded without deleting or
invalidating the last successful dataset. The scheduler defaults to 06:00 in
`Europe/Madrid` and is configurable through the `DATA_SYNC_*` variables.

The Java backend carries a port of this sync (`backend/.../application/datasync`), on in production since the 2D cutover
(`compose.yaml` sets it to `true`). Its switch is `BACKEND_DATA_SYNC_ENABLED` (default `false`), deliberately not Node's `DATA_SYNC_ENABLED`, so exporting
Node's `.env` into the Java process never starts a second syncer on the same database. `DATA_SYNC_HOUR`, `_MINUTE` and
`_TIMEZONE` are shared. `POKEAPI_BASE_URL` and `POKEAPI_SPRITE_BASE_URL` (https only, http only to loopback) exist for
tests.

## State and authority

The room state machine uses `LOBBY → game-owned phases → GAME_RESULTS → SESSION_RESULTS`. `GAME_RESULTS` is an obligatory, host-confirmed stop even when the session target has just been reached, so reconnecting clients always receive the last game's complete result before the session ranking. In a non-final session, continuing from `GAME_RESULTS` launches the same minigame in fixed mode or a compatible server-random minigame in random mode without passing through `LOBBY`. Player voting starts only after that confirmation and continues through `NEXT_GAME_VOTE → NEXT_GAME_VOTE_RESULTS`, then launches the compatible winner after its reveal. The coordinator falls back to `LOBBY` only when a changed player count leaves the configured rotation without enough compatible games. Round games use active/results phases; Pokémon Impostor uses `ROLE_REVEAL → ordered CLUE_PHASE turns → VOTING → VOTE_RESULTS → ELIMINATION`, while Type Duel owns its private type-selection, reveal and Pokémon-search phases. A game module owns every gameplay state; the room coordinator owns only the inter-game vote. There are no combinations of gameplay booleans.

`LiveRoom` owns only room lifecycle data: code, host, members, selected game id, per-game configurations, session progress and the optional active runtime. A `GameRuntime` captures the selected module, game id, stable participant roster, validated configuration and opaque module state. Room presence code uses that roster and never inspects a game's private state shape. Returning to the lobby discards that runtime and restores connected members to player status; it does not recreate the room or sockets. The room also keeps a session scoreboard independent from current connections plus a minimal public per-game history containing only game number, game id, winners and awarded points. This preserves final standings after departures without retaining or exposing opaque gameplay state. Totals cover the full session while the detailed history is capped to the 100 latest games so infinite sessions cannot grow every room snapshot without bound.

Session duration and minigame rotation are independent settings. Duration remains infinite, game-count based or point-target based. The host/co-host picks the session's minigames in the lobby as an ordered list (`gameSelectionMode.gameIds`, at least one, kept when the mode changes; `selectedGameId` is its first entry in the lobby and the running game afterwards). The order mode is `ORDER` (selection order, looping back to the start), `RANDOM` (server-random among the compatible entries, avoiding an immediate repeat) or `VOTE` (a 15-second vote between up to three server-sampled compatible entries; with only two it votes between both and with one it launches it directly). A single game in `ORDER` is the old fixed mode, and a legacy `{ type: 'FIXED' }` payload is parsed as `ORDER` with the current game. Selection only checks that games exist and are ported; player counts are checked at start (at least one compatible game, or the exact min/max message for a single game) and again before every launch and vote, where incompatible entries are skipped. The first game is the first compatible entry (random in `RANDOM`). Votes are accepted synchronously, immutable, private until resolution, and close early when every connected member has voted; ties use a server-side random choice. The winning minigame is revealed for three seconds before its preserved per-game configuration starts in the existing room.

Before the first launch from `LOBBY`, every connected non-host member must explicitly mark themselves ready. The host remains the only role allowed to start. Changing game, configuration, rotation or session format preserves readiness, as does a reconnect inside the grace period. Readiness is lobby coordination state only: it is cleared at launch and is not required for the automatic fixed, random or voting continuation between games.

The shared `GameRegistry` is additive and rejects duplicate ids. Its manifests are included in every public room view, so the lobby selector and client strategy registry use the same authoritative metadata. Selecting another manifest switches to that game's preserved configuration; starting a game instantiates only that module. Optional module facilities such as private asset resolution remain behind the same contract rather than adding game-specific branches to the room coordinator.

Registered users also own one persistent configuration per game id. The server loads this cache before accepting connections, seeds every newly hosted room from the creator's preferences and updates the acting registered host/co-host's entry after a validated lobby edit; guests continue to use registry defaults. Stored JSON is never trusted directly: it is merged only across keys present in the current default, validated by the current game schema and repaired branch-by-branch from current defaults when fields are added, removed or narrowed. Normalized legacy rows are written back during startup, so schema evolution cannot prevent room creation or mix settings between minigames.

Patch notes are PostgreSQL-backed `Changelog` records whose JSON content is validated by shared category contracts at every write and read boundary. The public endpoint returns only published versions ordered by release date; drafts and mutations live exclusively behind the administrator middleware. Browsers remember the latest version they opened to render the unread counter without adding tracking or coupling public release notes to a registered account.

Player feedback is stored as PostgreSQL-backed `Feedback` records with a validated general reference, optional game id, type, description and optional room code. A minigame reference requires a registered game id, while product-wide topics remain independent of the game registry. Both registered accounts and signed guest identities may submit through the rate-limited endpoint; the row keeps a display-name snapshot while only registered users receive a nullable database relation. Reading the inbox and moving entries through `NEW → REVIEWING → RESOLVED` is restricted to administrators. Feedback never enters room or game state, so reporting cannot affect timers, scoring or private projections.

Actions are handled synchronously in the Node event loop with no `await` before mutation. Consequently, concurrent votes in one room are serialized and a player's first valid vote is final. Runoff games share one eligibility, completion, vote-recording and leading-candidate implementation; starting a revote clears the authoritative ballot and increments a public vote-round number, which also invalidates pending client submission state. Every mutation produces one public projection plus a separate `getPlayerState` projection sent only to that player's socket. This keeps private roles and secrets out of shared room state. For horizontal scale, `InMemoryRoomStore` is the intentional replacement boundary: move rooms/timers to Redis and run each action under a per-room distributed lock or atomic Lua operation. Socket.IO's Redis adapter then distributes events.

The server stores an absolute deadline. Shared timed-round and cooldown helpers perform the common deadline, reveal and completion bookkeeping while each game injects its own transition strategy. Browsers only render an estimate through the shared server-clock hooks; the server timer calls `handleTimeout` and owns the transition.

## Reconnection policy

### Unanimous minigame skip

Every active `GameRuntime` owns `skipVoterIds`, a terminal `finishReason`, and definitive departures from its stable participant roster. The central `eligibleGameSkipVoterIds` includes eliminated participants and temporarily disconnected participants during the existing reconnect grace; it excludes definitive departures and identities that only joined as spectators. A definitive departure cannot regain eligibility by rejoining the same instance. Internal round changes never reset these votes. The inter-game selection vote retains its existing connected-member policy because it chooses the next roster, whereas skipping requires consent from the current roster.

`game:skip-vote:set` accepts a validated `{ gameInstanceId, wantsToSkip }` intention. The server derives the voter from the authenticated socket, sets or removes the vote idempotently, and checks that the nonempty eligible roster is entirely represented. Membership changes recalculate this before invoking the game presence hook. `room:state` and `session:restored` include `gameSkipState` with counts, voter ids, instance id, own vote and eligibility. The shared room layout renders the control once for all games, with reversible wording and an accessible live count.

Games start immediately: `room:start-game` (and every later launch in the session) creates the initial state and calls the engine's `start` in the same critical section. There is no intro phase, no `gameIntro` in the room view and no `game:intro:skip` event.

Normal completion and skipping both claim `finishReason` synchronously before further work; runtime identity guards and the existing timer-handle guard reject stale callbacks. Gameplay transport also carries `{ gameInstanceId, action }` so delayed actions cannot affect a replacement instance, including another instance of the same game. Deploy server and web together for this transport change. No engine requires knowledge of skipping or owns external timers: discarding its opaque runtime state, cancelling the room deadline and clearing the existing cursor channel releases the current game resources.

A skipped runtime is audited using the existing `ABANDONED` history status, without results, rewards, session points or an increment to completed games. Previous session results are retained; asynchronous persistence snapshots completed-game members before transitions can remove them. Skipping immediately invokes `advanceSessionAfterGame`, shared with host-confirmed normal continuation: the skipped game is excluded from the candidates, so order moves to the next entry, random picks another compatible game and voting opens the selection flow without it. If no other compatible game remains (for example a single-game session) or none can start, the session ends and `SESSION_RESULTS` shows the final standings; a skip never replays the same game nor falls back to the lobby. Normal continuation replays a single game. Only normally completed games stop at `GAME_RESULTS`; skipped games never display that screen. New runtimes start with empty skip votes and a fresh client component instance.

The signed HttpOnly identity cookie is stable through reloads. A disconnected member remains reserved for 30 seconds and receives the current public snapshot plus their own private game projection after reconnecting. After grace expires, host ownership transfers to the oldest connected member.

Presence has three room-level states: `CONNECTED`, `TEMPORARILY_DISCONNECTED` and `LEFT`. The shared game contract exposes one definition of an active, connected participant and a presence-change hook. Completion checks therefore wait only for connected required players; accepted votes, choices and clues remain immutable after their sender disconnects. Turn-based games skip an offline turn immediately, and in Type Duel, once the presence grace expires, the remaining duelist wins by forfeit (`DISCONNECT_FORFEIT`, +5, counted as a played duel); if both duelists are gone, the duel is cancelled without points (`DISCONNECTED`). Presence changes never re-enter a finished game or overwrite `GAME_RESULTS`/`SESSION_RESULTS`. A game whose manifest declares `presenceGraceMs` (`PRESENCE_GRACE_MS = 10_000` in Pokédex Distance, Shiny Quiz, Pokémon Impostor, Higher or Lower, Type Duel and Learnset Guess; `presenceGraceMs: 8000` in ¿Quién soy?) does not see a disconnect until that grace expires: the Java room keeps reporting the player as connected to the engine, the room view still shows them as reconnecting, and a per-member timer on the room lock applies the real presence change when it fires. A reconnect inside the grace cancels it, the reconnect grace still turns the member into `LEFT` if it expires first, and finishing or replacing the game cancels every pending presence grace. The grace never extends a deadline (`roundEndsAt` and the other engine timers are unchanged); it only prevents an early close, so a round can still resolve at its deadline with a player in grace counted as not having answered. Node's `manager.ts` ignores the field.

An active identity is retained in the running engine after grace expires when its historical state is needed for results, but it is no longer eligible for actions or future waits. A reconnect inside the 30-second grace restores the same private projection. Returning to the lobby keeps temporarily disconnected identities reserved until their own grace expires; definitive departures are removed. Host ownership transfers to the oldest connected member only after definitive departure, not on a transient socket loss.

The shiny answer is absent from the public state during voting. Candidate images use opaque, round-scoped application URLs; the server recolours decoys pixel by pixel with restrained HSL palette shifts, preserves neutral outlines and shading, and normalizes every candidate to the same crisp pixel-art PNG. Recolour metadata and semantic `/shiny/` source URLs never enter the public projection. Shiny Quiz only draws Pokémon that have an official `shinySprite`, and each round shuffles the decoy palettes with the game random source, so neither a fake base sprite nor a fixed palette order gives the answer away. `voteVisibility` decides when ballot targets go public: `REVEAL` (the default) exposes only completion ids while the round is open and the full ballots plus outcome rosters at the reveal; `LIVE` also exposes ballot targets during the round, and the lobby warns that it allows copying. Cumulative scores remain public. Each socket-specific projection retains only that player's accepted vote and reveal outcome for reconnect recovery. During the reveal (`revealSeconds`, 3–6 s, 4 by default; a stored config without it migrates to 4) the public projection adds the correct option, and only then does the client fetch the normal sprite through `/api/pokemon/{id}/sprite` for the before/after strip, while authoritative vote order awards correct voters 4/3/2/1 points with stable roster-order tie-breaking, so an earlier correct answer is always worth more.

Pokédex Distance keeps every pick and its National Dex number and distance in authoritative state until the round resolves. `selectionVisibility` decides what the public projection shows while a round or tiebreak is open: `HIDDEN` (the default) publishes only `selectedIds`, who has already picked, with empty `selections` and no Pokémon locks, so two players may choose the same Pokémon and receive the same distance; `LIVE` also publishes each pick's name and sprite and locks a chosen Pokémon for the rest of the round, and the lobby warns that it allows copying. In both modes the result (`lastRound`) reveals every pick, and each player's private projection confirms only their own pick. Because tied players may repeat the same pick, tiebreaks are capped at `MAX_TIEBREAK_DEPTH = 3`: a tie in the third tiebreak eliminates (as `FARTHEST`, with `tiedIds` kept) the tied players who picked last, or all of them when they picked at the same instant, so every game ends.

## Pokémon data

`prisma/seed.ts` imports exactly National Dex entries 1–1025 from PokéAPI once, including ordered types, all six base stats, physical measurements, official species colour, legendary/mythical classification, official Spanish names for normal and hidden abilities, evolution position, normalized move metadata, level-up learnsets and official flavor text explicitly tagged as Spanish. `extractSpanishAbilityName`, `extractCanonicalLevelUpEntries` and `extractSpanishPokedexEntries` are the acquisition boundaries; English ability names and English or unknown-version Pokédex text are discarded rather than translated. The server loads Pokémon, moves, learnsets and Pokédex entries into one indexed, immutable in-memory catalog at boot. Every registered game consumes this shared catalog; no game round, reveal or attempt calls an external service. Evolution branches use the maximum family depth while every terminal branch is normalized as final. The seed skips work once every dataset section is enriched, while `POKEMON_SYNC=true npm run db:seed` explicitly refreshes it.

Pokédle Race shuffles its configured canonical-form pool once with the game context random source. It assigns the shuffled entries without replacement; only when there are fewer valid entries than players does it cycle through the same shuffled order. This makes the restrictive-pool fallback deterministic for a deterministic random source. `secretPokemonIds` remains exclusively in opaque module state. Public and reconnect projections contain only accepted guesses, server-computed feedback and targets already revealed by a solve or by the end of the game. Each unresolved player receives one `GUESS` or explicit `NO_GUESS` row per synchronized round; disconnected players do not participate in the completion wait.

Pokémon Bingo derives numeric thresholds from quantiles of the configured pool and retains only conditions whose conjunction has real candidates. Every generated board is checked with an augmenting-path bipartite matching between cells and Pokémon; the game timer starts only after every player has a different board with a perfect matching. The matching itself and candidate ids remain opaque. Assign, replace and move intentions are applied synchronously as one server mutation, so a Pokémon is never visible in two cells of the same board. Incorrect attempts and cooldowns exist only in the per-player projection, while accepted assignments and progress are public. A completed board remains in its synchronized reveal for eight seconds; only the current room host may invoke the validated early-continuation action.

Learnset Guess takes the highest enabled Pokémon generation as its reference generation. At round creation the engine resolves and groups the entire canonical learnset, then publishes only groups whose reveal deadline has passed. The target id, name and sprite remain exclusively in opaque server state until `ROUND_RESULTS`; correct guesses publish only player id and solve order. Incorrect guesses are intentionally public and server-enforced cooldowns prevent spam.

Pokédex Entry Guess also takes the highest enabled generation as its reference. Its precomputed round deck selects only default Pokémon, preferring a Spanish entry at that generation or the newest prior generation. When no historical Spanish localization exists—notably for first- and second-generation games—it uses the earliest later Spanish entry available for that species. The server removes localized target-name aliases before publishing the text; the deck, target id, target name, sprite and correct attempts remain private until the synchronized four-second reveal. Regional and other forms are excluded until the catalog can associate them with genuinely distinct official entries.

¿Quién es ese Pokémon? uses only catalog entries with a trusted sprite and optionally includes the regional forms normalized by the seed. Its active public state contains an opaque per-game asset token rather than the target identity or source URL. The image proxy trims the alpha bounds, normalizes the shape into a 320×320 canvas and replaces every RGB pixel with black while preserving alpha. A different reveal asset id is rejected until `ROUND_RESULTS`, when the same authoritative target may be served in colour. Incorrect guesses are public; correct guesses publish only player id and solve order until the synchronized four-second reveal. One shared scoring function awards 1–10 points from remaining time plus a +3/+2/+1 podium bonus and provides the same breakdown rendered by the client.

Adivina el Grito reads `CRY_LATEST` and `CRY_LEGACY` references exclusively from the boot-time PostgreSQL audio catalog. The target id, selected version and source URL remain in opaque engine state. Active and reconnect projections expose only a round-scoped application audio URL; the room resolver validates its token and round before serving the trusted static asset. Correct guesses publish only player id and solve order until the four-second reveal. Pokémon without the configured cry lane are excluded before the game starts.

Pokémon Trivia creates every question synchronously from the immutable PostgreSQL-backed Pokémon catalog. Type, generation, BST, speed, height and weight questions select one unambiguous answer among three or four canonical Pokémon; question keys prevent repetition while alternatives remain. The correct option, explanation and all ballots stay in opaque module state during the round. Public and reconnect projections expose only the prompt, candidates and submitted-player ids, while each participant receives only their own locked answer. The server deadline determines scoring and reveals every answer atomically for four seconds.

Pokémon Impostor never includes `secretPokemonId`, the target sprite or the role map in its public projection. Living impostors receive `secretPokemon: null`; innocents receive only the display name and sprite in their socket-specific projection. Eliminated players may receive the reveal because the application has no spectator-to-player communication channel.

Type Duel follows the same boundary: public state reports only which participants have locked a type. Each participant receives only their own choice until both are committed, after which the game publishes the pair atomically. Exact type matching, cooldowns and the first winning attempt are resolved synchronously by the server.

Type Chain preloads the configured canonical and supported-form pool and reduces every transition to one shared rule: the set intersection between the previous and candidate types must contain exactly one element. Used ids are global to the current chain. Before every turn the server computes all unused continuations; an empty set starts a fresh, prevalidated chain without eliminating the waiting player. Turn acceptance, chain append and player advance happen in one synchronous room mutation, while timeouts and current-player disconnects remove that player from the circular order.

Guess from Stats builds each round from a normalized signature containing only enabled numeric stats and enabled public hints. Every configured-pool Pokémon with the same signature is stored as a private accepted answer, so hidden fields never affect correctness and indistinguishable forms are all valid. Active public and reconnect projections contain the signature's visible values but neither the source nor accepted ids; the complete equivalent set and each solver's selected answer appear only during the synchronized reveal.

Zoomed Pokémon keeps target identity and focus data in opaque state while publishing only the current camera stage. Correct answers retain the shared position score and add an authoritative zoom bonus of 4, 3, 2 or 1 points across the four progressive stages; resolving while the image is more enlarged is therefore worth more. The active projection exposes only the current bonus, while the reveal includes each solver's accepted stage, zoom and bonus breakdown.

PokéTaboo shuffles its stable participant roster once and cycles that descriptor order for the configured number of laps, so every participant describes before anyone repeats. The target id and its descriptive metadata remain in opaque module state; only the current descriptor receives a socket-specific `secretPokemon` projection. Guessers and spectators receive the descriptor identity, optional synchronized text hints, incorrect attempts and authoritative deadlines, while the exact target appears publicly only during the four-second reveal. Text hints are accepted only from the connected descriptor and are normalized before checking target display names, localized aliases and supported form ids. Guesses use exact catalog ids, so a regional form cannot be solved with its default species id. A descriptor disconnect cancels the turn without points and advances to the next available descriptor; guesser reconnects restore eligibility while the round is still active.

Sketchmon builds a separately shuffled drawer order for every configured lap. The target id remains opaque and only the current drawer receives its socket-specific name and sprite; guessers receive the normalized vector strokes, timed metadata hints and public incorrect attempts. Drawing clients batch validated start/append operations rather than sending canvas images. Pencil, eraser and flood fill are represented by the same vector protocol, with no artificial per-round stroke ceiling. The server owns snapshot-based undo and redo history, while the client serializes queued draw/history actions and overlays only the currently active optimistic stroke; the authoritative stroke list remains the reconnect snapshot and prevents coalesced socket updates from hiding accepted work. Reveal entries retain the final vector drawing, while the complete gallery is projected only at game results. Correct guesses end the round synchronously, award 5/4/3/2 points at the 20/40/60-second boundaries and award the drawer three points; a disconnected drawer consumes the turn without revealing the secret or awarding points.

Pokémon Connections publishes one shuffled Pokémon board while retaining its answer groups and category labels in opaque module state. Every participant resolves an independent private copy: found groups, mistakes and near-miss feedback travel only through that socket's player projection, while the shared projection exposes only per-player completion counts and status. Standard 12/16 boards prefer eligible curated templates; other valid combinations of three to five groups with three to five Pokémon use the bounded category-catalog generator. Exact server-side group matching awards one point per group plus the 3/2/1 completion podium, and synchronized timeout or completion reveals the complete solution before the next puzzle. Reconnection restores private progress without exposing it to other players.

Adivina por la Paleta keeps the target id, name and sprite private during the active round. The public projection contains only the persisted dominant colours, their normalized approximate weights, configured non-identifying hints and incorrect guesses; correct guesses publish the solver and order without exposing the answer. Palette metadata v3 retains up to eight representative colours and forces older unweighted palettes through DataSync again. The configured size acts as a display maximum, so a Pokémon with fewer persisted colours shows all of them instead of being excluded. Generation, types, type count, evolution stage and legendary classification can be enabled independently by the host, while the complete identity appears only during the synchronized reveal.

Pokémon Team Auction exposes one ascending, visible auction for each of exactly six lots per player. The pool is shuffled from the configured generation/form catalog and cycles only when fewer than 6×players unique entries exist. Bids start at one, accept arbitrary positive jumps, and are immutable public events; passing removes a player only from the current lot, while disconnected or unaffordable participants are skipped. The high bidder's team and balance update immediately, completed teams stop bidding, and lots with no valid opening bid are retained as explicitly unowned results. Final standings compare team BST, remaining coins, legendary count and mythical count; an identical tie key produces joint winners.

Secret Ranking publishes the shared five-Pokémon board and subjective prompt while retaining every submitted order in opaque module state. Active public and reconnect projections expose only which players have locked an answer; each participant receives only their own immutable ranking. At synchronized completion or timeout, missing answers receive no points and are excluded from the average. Each submitted player is scored with Spearman footrule distance against the mean positions of the other submitted rankings, explicitly excluding their own order. Competition-ranked proximity awards the shared dynamic position points, and the reveal publishes the group consensus, individual orders, distances and round points for eight seconds. Official and enabled host-owned prompts share the existing data-only subjective catalog boundary and avoid repetition while unused entries remain.

Most Likely To keeps each Pokémon choice opaque until every connected required player answers or the selection timer expires; active public state exposes only completion ids and each socket receives only its own replaceable choice. The voting projection then reveals author and Pokémon together, retaining duplicate Pokémon as independent authored answers. Ballot targets remain private while only voter completion is public, self-votes are rejected, and disconnected players stop blocking either barrier without deleting accepted input. A first-place tie produces one revote restricted to the tied authors; a persistent tie becomes a shared victory. Only winning authors receive three points, including every author in a shared victory, and the synchronized result reveals all decisive ballots before advancing.

Would You Rather Pokémon sends each participant one immutable ballot containing a preference and a majority prediction. During the active round, the shared projection includes only the two public situations and submitted-player ids; each socket can recover only its own ballot after reconnecting. Submitted preferences—including the voter's own—form the authoritative majority, while missing ballots are excluded. A strict majority awards one point to matching preferences and two to matching predictions; an exact tie awards neither kind of point. The synchronized reveal publishes totals and every submitted preference/prediction. Official pairs remain data-only, while registered hosts own a separate persistent pair catalog so its two-option structure never leaks into the generic subjective-question pool. The persistent catalog accepts a versioned, strict JSON batch schema, validates duplicates before writes and reports field paths back to the configuration UI.

Pokémon Red Flag / Green Flag draws its protagonist from a server-shuffled generation/form pool and chooses the configured negative, positive or server-random 50/50 prompt. It preassigns shuffled opaque answer ids that cannot be correlated with participant order, caps text at 100 characters and stores each in-progress draft only in opaque state and its author's socket projection. At the authoritative deadline the last non-empty synchronized draft becomes an answer; an empty draft does not. Submitted text is immutable, and voting entries are shuffled once before their text and opaque id become public without author identity. Ballot targets are likewise private, self-votes are rejected through the hidden author mapping and disconnected players stop blocking both barriers without erasing accepted input. A tied first vote narrows the anonymous candidates to one revote, while a persistent tie awards a shared three-point victory. Only the synchronized round result reveals authors, decisive ballots and missing responses.

One of Us Is Fake keeps the fake id and both category ids exclusively in opaque game state. Before the final round reveal, each socket-specific projection contains only that participant's category and, when enabled, a positive `isFake` marker sent solely to the fake. Pokémon choices are validated only against the configured catalog pool—categories remain subjective data and never acquire Pokémon rules. The public projection exposes completion ids during selection, reveals choices one at a time in a server-shuffled order, and later exposes only who has voted rather than ballot targets. Ties narrow to their leading candidates across revotes; an unchanged tie is broken with the server random source. Disconnected players stop blocking each completion barrier, while their committed choices and votes remain part of the round.

Pokémon Bluff Auction reuses Pokémon Bingo's objective condition language and matcher, adding stable National Dex catalogs for canine, feline, starter, fossil, pseudolegendary and Ultra Beast categories. Legendary and mythical conditions continue to use seeded species metadata. Candidate ids and the real solution count remain inside opaque module state. Its canonical pool explicitly rejects non-default forms and duplicate National Dex numbers. The auction accepts only ordered, strictly increasing bids and converts confirmed passes or disconnected auction turns into irrevocable round exits; the last remaining participant enters demonstration without a challenge action. Each unique submitted Pokémon is validated synchronously: a correct answer extends the existing absolute deadline by five seconds and an incorrect answer removes three seconds, resolving the timeout immediately if the penalty exhausts the clock. Duplicates are public attempts that grant neither credit nor a time change. The demonstration search exposes at most five ranked matches. An impossible bid resolves only after the auction, at which point the result serializer may reveal the real solution count. Temporary bidder disconnects preserve deadline and attempts; definitive departure resolves a team win for everyone else.

Registered hosts own persistent `CustomCategory` rows. A boot-loaded server cache keeps room mutations synchronous: lobbies receive only the host's enabled count for validation, and game creation receives an immutable text/id snapshot. CRUD writes update PostgreSQL first and then notify hosted lobbies. Official prompts live in data-only Java classes (`*Prompts.java`, `OneOfUsIsFakeCategories.java`), separate from game rules; the engine combines that catalog with the host snapshot according to configuration and avoids reused prompts while unused ones remain.

## Security boundaries

Passwords use bcrypt cost 12. Identity is an expiring HS256 token in an HttpOnly SameSite cookie. HTTP and socket events are rate-limited, payloads are size-limited, shared Zod schemas validate input, and every host action checks current ownership. In production, use TLS at Cloudflare/reverse proxy, set `COOKIE_SECURE=true`, use a random secret, restrict the origin and keep PostgreSQL private.


## Runtime and command revisions

Each registered engine implements `getLifecycle`: phase, next deadline, action epoch and spectator IDs. The coordinator treats engine state as `unknown`; game-owned cursor authorization is exposed through `getCursorChannel`, while the transport adapter owns routing and rate limits. `game:action` requires both `gameInstanceId` and `actionEpoch`. The epoch changes when the phase, round, turn or revote changes, but not when a demonstration earns additional time. A rejected action may return a transitioned state; the coordinator synchronizes it before replying with the rejection.

The web command sender uses the shared Socket.IO signatures, rejects offline sends, waits at most eight seconds for an acknowledgement and settles on disconnect. It never automatically replays a command after an unknown outcome. The client must receive the authoritative room state before the user decides whether to retry. Server and web must be deployed together for this envelope change.

Room snapshots carry `roomInstanceId` and a monotonic `revision`. Each broadcast builds its common projection once and attaches player-specific state separately. The browser ignores older revisions of the same room instance, including snapshots arriving in delayed acknowledgements. Reconnection still receives a complete snapshot. Drawing deltas are not implemented yet.

## Resource and shutdown budgets

Sketchmon stores shared immutable drawing snapshots: at most 16,384 points, 1,024 strokes, 64 undo steps and 12 gallery entries. A batch that would exceed a drawing limit is rejected atomically. The image cache retains at most 256 entries / 32 MiB, deduplicates pending requests and permits eight concurrent loaders with 64 pending requests in total. Remote images have a 15-second deadline and an 8 MiB download limit; synchronization responses default to 30 seconds and 16 MiB. These are operational safeguards, not a measured capacity guarantee.

Shutdown stops the scheduler and room timers, closes Socket.IO, drains accepted result/audit tasks, preferences and active synchronizations, then marks unfinished activity interrupted and disconnects Prisma. It is idempotent for repeated signals. Failures remain logged; draining is not a durable outbox and cannot recover results lost during a process crash. No hard shutdown deadline is imposed while accepted synchronizations remain active.

Deploy one authoritative server process. Room state includes executable modules, Maps/Sets, promises and timer handles. Redis is not a direct replacement for this store. Global startup recovery and user caches must gain ownership/invalidation before enabling multiple instances.

## Session scoring and bounded choices

`POSITION_V1` keeps raw game scores for profiles and per-game results. Session history stores both `rawPoints` and awarded `points`. Positive-scoring standings receive `pointsForPosition(numberOfStandings, position)`; zero-scoring standings receive zero. Equal positions receive equal awards. Thus raw BST and correct-answer units never mix directly in session totals. Session targets now refer to these normalized awards.

Team Auction and Bluff Auction use a 20-second bid-turn limit by default and automatically pass when time expires. Setting `bidSeconds` to zero explicitly selects an untimed game. Who Is Who allows 30 seconds by default for manual secret selection, fills missing selections randomly on expiry and then begins the first playing turn. `selectionSeconds: 0` allows untimed selection. Older saved configurations acquire these new defaults through schema/config normalization.

## Browser package boundary and verification

`@pokemon-universe/shared/public` is the package's only entry, for web code and tests alike; engines live only in Java. `npm run check:boundaries` walks the runtime import graph of that entry and rejects any dependency other than `zod`; `npm test` runs that check and rebuilds shared before testing consumers.

PostgreSQL tests run in the Java backend against a disposable Testcontainers database (`cd backend && ./gradlew check`); they never use a developer's `DATABASE_URL`.
